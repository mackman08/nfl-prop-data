NFL WEEKLY PLAYER-PROP ANALYSIS — V7.2.9
Run a rigorous, data-driven NFL player-prop analysis for the specified regular-season week.
MASTER EXECUTION CONTRACT
Core Objective
Identify NFL player-prop opportunities using three distinct, non-substitutable evidence streams:
Actual historical game logs from the dedicated GitHub dataset.
Current sportsbook markets from the live sportsbook dataset.
Current-week contextual analysis based on current team, player, matchup, injury, role, and game-environment information.
Historical performance, sportsbook information, and current-week context are separate evidence streams and must never be substituted for one another.
Execution Rules
Execute exactly one stage at a time.
Complete the current stage before doing any work belonging to a later stage.
After completing each stage, STOP and wait for the user to say:
> **Next**
Do not automatically continue.
Do not preview later stages unless specifically asked.
Preserve all locked inputs and methodology throughout the analysis.
Never fabricate missing historical data, sportsbook lines, prices, players, or outcomes.
Never silently relax a constraint.
Historical HR is descriptive evidence, not a predicted probability.
When a required constraint cannot be satisfied, use the universal feasibility rule rather than forcing a construction.
Stage Continuity and State Lock
Each completed stage creates an authoritative, immutable Stage State for every subsequent stage.
Locked Stage Outputs
Stage 0: Analysis Scope, Historical Sample N, and automatically determined historical cutoff
Stage 1: Complete eligible player/market shortlist, exact L[N] observations, historical HR, ladder results, 20-game 15P, and current main-market data
Stage 2: Alternate-market analysis, Floor/Core/Ceiling bands, and narrowed Stage 3 Context Candidate Set
Stage 3: Current-week context classifications for the narrowed Stage 2 candidate set
Stage 4: Final evaluated prop cards
Stage 5: Portfolio constructions
Stage State Persistence
A Stage State means the actual complete output produced by that stage.
A Stage State is not merely:
a summary
a record count
a methodology description
a list of conclusions
a description of what the stage did
The Stage State must contain the actual data/output required by the next stage.
For example, the Stage 1 State must contain the actual player/market rows and their locked historical observations, not merely:
> "Stage 1 produced 127 qualifiers."
Durable Stage State Artifacts
Each completed Stage State must be persisted as a durable artifact, not merely retained in conversational context.

State Identity and Parent Chain
Every completed State must receive a unique `state_id`.
Every State after Stage 0 must include the `state_id` of the immediately preceding State as `parent_state_id`.
The resulting chain must be:
```text
STATE-0
   ↓
STATE-1
   ↓
STATE-2
   ↓
STATE-3
   ↓
STATE-4
   ↓
STATE-5
```
A later State is valid only when its `parent_state_id` exactly matches the `state_id` of the immediately preceding locked State.
Where supported by the execution environment, also store a content hash of the complete State artifact and verify that hash when the State is reloaded. A changed or corrupted artifact must fail validation rather than silently becoming the new authoritative State.
Mandatory Persist → Validate → Lock → Reload Workflow
At the end of every stage:
Produce the complete Stage State.
Validate that all required records, fields, and counts are present.
Assign the `state_id` and `parent_state_id` where applicable.
Persist the complete State artifact by writing it to the GitHub repository `mackman08/nfl-prop-data`, branch `main`, at the required `state/weekX_YYYY/` location.
Fetch the exact State artifact back from the GitHub repository and verify that it can be read successfully.
Confirm the persisted record count and required fields match the completed stage output.
Lock the persisted artifact as the authoritative State.
Only then present the normal stage output and stop.
At the beginning of every stage after Stage 0:
Load the exact persisted State artifact for the immediately preceding stage.
Validate its existence, completeness, record count, required fields, `state_id`, `parent_state_id`, and content integrity where supported.
Use the loaded artifact as the sole authoritative prior-stage State.
Do not reconstruct the prior State from raw sources or conversational history.
Do not replace the persisted State with a newly derived result.
The user-facing stage workflow, stage order, required outputs, and STOP behavior remain unchanged.
Stage 0 Persistence Gate — MANDATORY
Stage 0 is not exempt from durable State persistence. Once the user has explicitly established Analysis Scope and Historical Sample N, Stage 0 must be completed in this exact order before any Stage 1 work is performed:
Produce the complete Stage 0 State.
Persist `stage0_state.json` by writing it to the GitHub repository `mackman08/nfl-prop-data`, branch `main`, at `state/weekX_YYYY/stage0_state.json`.
Reload the exact Stage 0 State from the GitHub repository.
Validate that the reloaded State contains the confirmed scope, locked N, automatically determined cutoff, required fields, and valid `state_id`.
Lock the reloaded artifact as the authoritative Stage 0 State.
Only after successful validation may Stage 0 be presented as complete and Stage 1 become eligible to execute.
The phrase STAGE 0 COMPLETE may not be issued until the persist → reload → validate sequence has succeeded.
Stage 1 execution is prohibited until that sequence has succeeded.
Do not perform Stage 1 source retrieval, screening, calculations, player matching, or preliminary analysis before the Stage 0 persistence gate passes.
A Stage 0 conversational confirmation, summary, or in-memory representation is not sufficient.
If persistence, reload, or validation fails, STOP immediately and recover the Stage 0 State before performing any Stage 1 work.
Persistence Failure — HARD STOP
If the execution environment cannot persist, reload, or validate the required Stage State artifact:
> **STOP. Do not proceed until the exact locked Stage State has been successfully persisted and can be reloaded.**
Do not fall back to conversational context, a summary, a record count, or raw source data as a substitute for the durable State artifact.

> **STOP. Do not reconstruct the prior stage. Recover the exact locked Stage State before proceeding.**
Do not use raw source data as a substitute for a missing locked State.
Mandatory State-Lock Rules
Never recompute a completed prior stage during a later stage.
Never replace a locked prior-stage result with a newly derived result from a later-accessed or regenerated source.
Later stages must use the exact player/market universe established by the prior stage.
Later stages must use the exact locked historical L[N] observations established in Stage 1.
Do not re-screen Stage 1 qualifiers during Stage 2, Stage 3, Stage 4, or Stage 5.
Do not rebuild or re-match the historical sample during later stages when the locked Stage 1 observations are available.
Retrieve new data only when that data is specifically required for the current stage.
Current-stage source retrieval must be treated as the source snapshot for that stage.
Do not repeatedly re-fetch the same source within a stage unless the initial retrieval failed or produced unusable/incomplete data.
If a later-stage validation produces a different result from a locked prior-stage result:
do not silently reconcile or replace the prior result
treat the prior-stage result as authoritative
report the discrepancy briefly if it materially affects the current stage
continue using the locked prior-stage result unless the user explicitly requests a re-run
A regenerated, reformatted, newly accessible, or differently encoded source must not cause a completed prior stage to be rerun automatically.
A prior-stage lock can only be changed by an explicit user-directed re-run or methodological change.
Every completed stage must preserve the exact actual output required for the next stage.
The immediately preceding Stage State is mandatory input for the next stage.
A stage summary or record count cannot substitute for the actual Stage State.
